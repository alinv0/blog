# When the AI Gets It Wrong: Debugging Code You Didn't Write

## The reps nobody's counting are the ones that compound fastest

The strongest engineers I have worked with weren't the ones writing the most code, but the ones spending their mornings stepping through AI-generated pull requests, tracing logic that looks right but isn't, and fixing bugs that no human would have written. This is the highest-leverage skill-building activity happening in engineering right now, and almost nobody talks about it that way.

Here's the uncomfortable claim: debugging AI-generated code is building stronger first-principles reasoning than writing code from scratch. I can't point to a longitudinal study that proves it — nobody's run that experiment yet. But the structural conditions are all there. I'm not talking about novel greenfield systems design — that's a small fraction of most engineers' working hours. I'm talking about the 80% of engineering work that's extending, maintaining, and integrating existing systems.

Back in early 2024, GitClear's [analysis of 153 million changed lines of code](https://www.gitclear.com/coding_on_copilot_data_shows_ais_downward_pressure_on_code_quality) flagged the first large-scale signal: code churn — lines reverted or updated within two weeks of being authored — was projected to double compared to the 2021 pre-AI baseline. That was the canary. Two years later, updated large-scale churn data is scarce, but the directional trend is undeniable to anyone working in a codebase with AI-assisted contributors. In my own repositories, the ratio of fix commits to feature commits has roughly doubled since I started using AI-assisted coding in late 2023 — and my teammates report the same pattern. Code arrives faster and breaks differently.

More time in the debugger doesn't automatically mean more learning. But if you're doing that work with intent — tracing root causes, not just patching symptoms — the reps compound. The rest of this article is my case for why.

Think about what the last decade actually trained engineers to do. [Stack Overflow](http://stackoverflow.com) gave us a generation of copy-paste development: find the snippet with the most upvotes, drop it in, move on. Stepping through that code line by line wasn't part of the workflow. It compiled, the tests passed, you shipped. That was the reasonable thing to do.

AI-generated code demands something different. As Charity Majors [puts it bluntly](https://stackoverflow.blog/2024/06/10/generative-ai-is-not-going-to-build-your-engineering-team-for-you/): "you cannot trust generated code. I can't emphasize this enough. AI-generated code always looks quite plausible, but even when it kind of works, it's rarely congruent with your wants and needs." She's right — you have to step through the output line by line, revising as you go, before you can commit it, let alone ship it.

That line-by-line stepping is the exact deep reading practice that copy-paste culture nearly killed. And it's not a side effect to manage — it's a training signal to exploit.

## There's no 'ask the author' anymore

When you inherit a legacy module from a departed teammate, you still have options. You read the commit history. You search Slack. You find the original PR discussion where someone asked "why not use an event-driven approach here?" and the author explained the constraint. With AI-generated code, those artifacts are thin at best. Yes, tools like Cursor and Claude Code now maintain session context and can explain their reasoning — but that's reconstructed context, not genuine design rationale. There's no trail of rejected alternatives, no debate about tradeoffs, no "I tried X and it broke under load so I went with Y." You have source, behavior, and a model's post-hoc justification. That's not the same thing as understanding why.

This forensic skill — reconstructing intent from behavior alone — is what separates engineers who can parachute into any codebase from those who only function in code they wrote. Before AI tools, you encountered this challenge a handful of times per career: a new job, a company acquisition, diving deep into an unfamiliar open-source project. Now it's every day.

[GitLab's 2026 Global DevSecOps Report](https://about.gitlab.com/developer-survey/), surveying 3,266 practitioners, found that 34% of code is now AI-generated, 37% is written from scratch, and 29% is copied from other sources. A third of production code was generated by a model that had no design rationale for its choices. Even when humans review that code before merging — and let's be honest, most AI-code reviews are cursory approval of plausible-looking output — the deep "why" remains absent from the project's institutional memory.

I used to think this was an annoying chore — the tax you pay for faster code generation. I was wrong. The moment that flipped it for me was a production incident: I traced a subtle request-routing bug in a service I'd never touched. A header-based routing rule was matching on `X-Forwarded-For` instead of the actual client IP, which worked fine behind a single proxy but produced silent misroutes once requests hit a multi-hop proxy chain. I diagnosed it in half the time it would have taken me two years ago. The reason was obvious — I'd been doing exactly this kind of forensic reasoning on AI pull requests every single day.

I used to get that workout a few times a year. Now I get it before lunch.

## AI bugs are a different species

AI-generated bugs aren't just more frequent. They're structurally different from human-written bugs in a way that makes them more instructive, not less.

A human developer's bugs correlate with their known weaknesses. If your teammate always forgets null checks, you learn to look for null checks. If they're sloppy with async error handling, you know where to probe. AI bugs don't follow that pattern. They exploit the gap between surface plausibility and actual correctness — the code looks like it was written by someone who knows what they're doing, but it embeds failures that such a person would never make.

Research flagged this pattern early. A [Stanford/NYU study](https://arxiv.org/abs/2211.03622) found that participants with AI coding assistants wrote significantly less secure code — and were *more confident* it was secure. [Pearce et al.](https://arxiv.org/abs/2108.09293) found roughly 40% of Copilot's security-relevant completions were vulnerable — not random garbage, but plausible code embedding exploitable weaknesses. Both studies tested early-generation models (2021–2022), and no comparable large-scale study has been published on current-generation systems — which suggests the industry has moved on to deploying these tools faster than studying their failure modes. But the structural argument holds: these systems optimize for plausibility, not correctness. That's not a bug in any particular model — it's an architectural property of how autoregressive language models produce code. They select tokens that are statistically likely given context, not tokens that are provably correct given constraints. Yes, reasoning-augmented models and chain-of-thought are narrowing this gap for well-specified problems. But the invariant-class bugs I'm describing live precisely where specifications are implicit — in semantic contracts, domain assumptions, and interaction effects that no prompt fully captures. More fluent output makes the overconfidence problem worse, not better, because the surface quality makes failures harder to spot.

I hit this in one of my projects — a small service that ranked and deduplicated user-submitted entries by score. The AI generated a `TreeSet<Entry>` with `Comparator.comparing(Entry::getScore)` to maintain a sorted collection of unique entries. Correct generics, correct method references, clean syntax. But `TreeSet` uses the comparator — not `equals()` — to determine element identity. Two entries with the same score but different IDs and different authors were treated as duplicates. The set silently dropped records. The output had the right type, a reasonable-looking size, and sorted order. I didn't catch it until a week later when I noticed the entry count was consistently lower than expected and stepped through the comparator contract in the `TreeSet` Javadoc. No human who actually understood sorted collections in Java would write that bug, because anyone who knows `TreeSet` knows the comparator *is* the equality check. The AI knew the API but not the invariant.

Debugging that forced me to re-examine exactly how `TreeSet`'s comparator contract interacts with element identity — the section of the Javadoc I'd skimmed past for a decade. Each structurally novel bug like this forces you back to fundamentals you'd stopped questioning. That's where the growth is.

## Writing code is assembling from the manual

There's a reason debugging teaches faster than writing, and it's not complicated.

Think of it like mechanical work. When you write code, you're assembling a machine from a manual — bolt A to bracket B, torque to spec, move on. You never learn why that bracket is shaped the way it is or what happens at harmonic frequencies you'll never hit in the test rig. When you debug AI-generated code, you're diagnosing why an assembled machine vibrates at certain RPMs. You're forced to reason about load paths, resonance, and material properties — the physics beneath the assembly steps. One afternoon of that teaches you more about how machines work than a month of following instructions.

Writing code reinforces existing mental models. You reach for the patterns you already know. You solve problems the way you've solved them before. That's fine for shipping — it's not fine for growing. Debugging someone else's wrong solution forces you to build new mental models from the ground up.

Birgitta Böckeler, in a [memo on Martin Fowler's site](https://martinfowler.com/articles/exploring-gen-ai/08-how-to-tackle-unreliability.html), characterizes the AI coding assistant as "very well-read, but inexperienced" — high intelligence, low wisdom in D&D terms. Wisdom in D&D means knowing which spell to cast in *this* fight, not which spells exist. That's the gap debugging forces you to close. The AI applies patterns from millions of repositories without understanding which pattern fits your specific context. When it picks the wrong one, you can't just reject it — you have to understand *why* it's wrong, which means stress-testing the boundaries of abstractions you've used for years but never interrogated.

This is where the learning happens: operating at the edge of your current ability with immediate feedback. Writing the CRUD endpoint you've built fifty times doesn't push that edge — it's repetition. Debugging AI code that uses an unfamiliar pattern or makes a subtle error in a domain you thought you understood? That's the edge. And the failing test gives you the feedback loop.

## Most AI bugs are noise — here's how to find the signal

The strongest practical objection to everything I've said is simple: most AI bugs are shallow and tedious. Hallucinated APIs. Wrong argument order. Missing imports. That's not "first-principles reasoning" — it's babysitting.

And that objection is right — by count. I'd estimate 60–70% of what I fix in AI output is typo-class noise. But count isn't time. A typo-class bug takes under 2 minutes to fix. An invariant-class bug — where the logic is structurally plausible but semantically wrong — takes 10–45 minutes. Run the math on a typical week: if I fix 20 typo-class bugs (40 minutes total) and 8 invariant-class bugs (4+ hours total), the majority of my debugging *time* is spent on high-learning work. The noise is frequent but cheap. The signal is rarer but dominates the clock. Your split will vary by language, domain, and how much context you feed the model — a TypeScript developer with strict typing will see fewer invariant-class bugs than someone working in Python or Ruby, because the type system catches a class of errors before they reach the debugger.

Here's the framework I use. After every AI debugging session, I tag the bug into one of three categories:

**Category 1: Typo-class.** Hallucinated API, wrong argument order, missing import. Fix time under 2 minutes. Learning value near zero.

**Category 2: Invariant-class.** Code that compiles and runs but violates a semantic contract — wrong join key behavior, incorrect boundary condition, a race condition hidden by plausible structure. Fix time 10–45 minutes. High learning value.

**Category 3: Architecture-class.** The AI picked a fundamentally wrong approach — chose inheritance where composition was needed, used polling where events were required, built a synchronous pipeline for an inherently async workflow. Fix time varies, but the learning is in the recognition, not the fix.

The diagnostic is simple: if more than half your AI bugs are Category 1, you're using the wrong tool or the wrong prompts. If you're hitting Category 2 and 3 regularly, you're in the training zone. Track the ratio weekly.

## Doesn't this just teach you to spot failure?

One counterpoint worth addressing head-on: debugging bad code teaches you to recognize failure, not to design well. This is the strongest version of the objection, and it's partially right. You won't learn system design by debugging alone. But debugging builds the diagnostic substrate that informs design. A structural engineer who has investigated ten building collapses understands load distribution in a way that someone who only designed on paper never will. The failure analysis doesn't replace design skill — it feeds it. An engineer who has traced a subtle concurrency bug through AI-generated async code now has visceral knowledge of why certain async patterns are fragile. That knowledge directly improves their next architecture decision.

And yes — you can use AI to help debug AI-generated code. I do it constantly. I paste stack traces into Claude, ask it to hypothesize root causes, use AI-powered code review on PRs. But here's what doesn't change: I still have to evaluate whether the AI's diagnosis is correct. I still have to decide which hypothesis to investigate first. I still have to confirm the fix actually addresses the root cause and doesn't mask it. Using AI to debug is like using a calculator to check your math — it speeds up verification, but it doesn't build numerical intuition for you. The cognitive demand on the engineer stays the same. The tool changes; the judgment doesn't.

## The scarcest skill isn't prompting — it's reading

Stack Overflow's [2025 Developer Survey](https://survey.stackoverflow.co/2025/) confirms the trajectory: 84% of developers now use or plan to use AI tools in their workflow, up from 76% in 2024 and 62% in mid-2024's initial measurement. But trust hasn't kept pace with adoption — more developers actively distrust AI output accuracy (46%) than trust it (33%). Positive sentiment toward AI tools actually *declined* from over 70% in 2023–2024 to 60% in 2025. And the most cited frustration, at 66%, is dealing with "AI solutions that are almost right, but not quite" — with 45% calling out that debugging AI-generated code is more time-consuming. AI-generated code volume is scaling far faster than confidence in its correctness. The verification work stays human.

Charity Majors [nails the real hierarchy](https://stackoverflow.blog/2024/06/10/generative-ai-is-not-going-to-build-your-engineering-team-for-you/): "Writing code is the easiest part of software engineering, and it's getting easier by the day. The hard parts are what you do with that code — operating it, understanding it, extending it, and governing it over its entire lifecycle." If writing code is what AI accelerates, then the skills that remain scarce are exactly the ones debugging exercises: reading code critically, tracing execution through unfamiliar paths, reasoning about why a system behaves the way it does under constraints.

The engineers debugging the most AI code today are building the scarcest skill of the next five years. Not prompt engineering — that's already commoditized. Not playing architecture astronaut — grand designs still need someone who can read the code they produce. The compound interest on forensic reasoning is just starting to accumulate. Five years from now, when AI generates 60 or 70 percent of production code, the engineers who spent 2024–2026 doing the unglamorous work of tracing, diagnosing, and understanding will be the ones trusted to make decisions about systems nobody fully wrote. That's not a prediction about AI's limits. It's a prediction about which human skills remain load-bearing.
